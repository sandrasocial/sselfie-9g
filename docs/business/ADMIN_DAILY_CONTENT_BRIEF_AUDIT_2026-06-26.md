## Current Implementation

The weekly admin content brief is generated by `lib/content-engine/brief-generator.ts`.

It uses:

- Instagram Graph API data from Sandra's own account via `collectInstagramPerformance()`
- prompt-copy and Vault behavior from `analytics_events` via `collectAudienceSignals()`
- Sandra's canonical Story Bank and measured prompt/funnel behavior
- Vault inventory from static prompt data + published Vault collections
- SUITE product catalog from Academy entitlements
- Anthropic web search for a generic current hook/content-strategy memo

It stores the generated brief in `analytics_reports` as `content_brief_weekly`.

## Main Finding

The brief is too self-referential.

It correctly identifies high-performing topics and pillars from Sandra's own content, but the prompt previously told the model that Sandra's own top posts should "win" over research. That made the model treat her past winning visuals as the safest recommendation.

Result: it keeps suggesting similar visual executions instead of translating the winning topic into a fresh creative treatment.

Latest stored brief examples from 2026-06-26:

- another clean girl mirror selfie
- another dark feminine cafe prompt demo
- another half-light Vogue/window shot
- another "ChatGPT turned my selfie into this" reveal

Those can be valid pillars, but they should not automatically reuse the same scene, crop, location, or outfit energy.

## Data-Quality Issue Found

The latest stored brief also included a fabricated income-style hook:

> "I make €3,200 this month from my phone while my kids were at school."

That number was not supplied by the content brief data packet as a verified Stripe or revenue source.

This is not acceptable for admin recommendations because it can lead to inaccurate public claims. The generator now has an explicit rule: never invent specific earnings, revenue amounts, client counts, follower gains, or conversion numbers.

## Fix Applied In This Pass

Updated `lib/content-engine/brief-generator.ts` only.

Changes:

1. Added a concise `MARKET_PATTERN_CONTEXT` from the recent internal competitor research.
2. Added that context to the content brief data packet.
3. Updated the research prompt to ask for current hook formats, creator mechanics, and fresh visual-treatment notes.
4. Updated the final brief-generation rules:
   - own top posts win for topic, pillar, hook mechanic, and CTA
   - own top posts do not win for repeating the same visual scene
   - same pillar is allowed, same visual execution is not
   - each piece must use a fresh creative treatment
   - use similar-creator mechanics without copying their exact visuals or positioning
   - never invent specific money/results numbers

## What This Should Improve

The brief should now say, in effect:

- This topic is working.
- This audience signal is real.
- This format is working in the market.
- Here is a fresh way to express it visually.

Instead of:

- This reel worked.
- Post the same visual again.

## What Still Needs A Better System

The best version is a small competitor/similar-creator intelligence layer, not just a prompt patch.

Recommended next build:

1. Create a curated watchlist source for 5-10 similar/adjacent creators.
2. Store weekly observations as structured rows:
   - creator
   - post URL
   - format
   - hook mechanic
   - visual treatment
   - CTA mechanic
   - why it is relevant to Sandra
   - what not to copy
3. Feed those rows into `/admin/content-brief`.
4. Add UI labels that separate:
   - winning pillar
   - market mechanic
   - fresh visual treatment
   - do-not-repeat note

## Verdict

The admin content brief is useful for finding demand signals, but it was not strict enough about creative variety.

Current issue:

- good at "what topic is working"
- weak at "how do we express this in a fresh way"
- not truly connected to similar-creator data yet
- one stale trend system exists but should not be reused as-is

After this pass, the generator should produce less repetitive visual advice, but the real long-term fix is adding a structured creator-watchlist input.
